# Rule 20: Cross-Runtime Context Handoff and Lifecycle Governance

## 1. Authority and Derived State

1. `ATOMIC_TICKET.md` and `plans/plan.md` are the sole primary planning authorities (`atomic_tasks.md` remains secondary/consolidated).
2. `HANDOFF.md` is strictly a derived, non-authoritative capsule under `HandoffSnapshotV1`, generated by the authorized handoff operator only after Lead BA updates the canonical ticket and plan. QA, developer, DevOps, and reviewers may request this checkpoint but never write the ticket, plan, or handoff.
3. Handoff generation captures objective, HEAD/worktree, all task states, decisions/constraints, plan paths, exact commands/results, failures/risks, next action, owners/skills, and sanitized quota evidence.
4. The engine never parses a raw transcript; only bounded state is evaluated.
5. Any unresolved lane forces `clear_ready` false; unverified metrics evaluate to `UNKNOWN`.

## 2. Quantitative Bounds

1. State input payloads are strictly bounded to `64 KiB`.
2. Derived handoff capsules must not exceed `16 KiB`.
3. Percentage thresholds: alert at `40%`, snapshot at `45%`, critical at `80%`. Remaining percentage semantics govern dispatch: alert/reassess at `<=40%`, snapshot at `<=20%`, freeze-and-handoff at `<10%`.
4. Transcript byte thresholds: alert at `400 KiB`, snapshot at `450 KiB`, critical at `900 KiB`.

## 3. Operator Actions and Native Hook Trust

1. Only an `operator` may clear, compact, or reset sessions; hooks cannot automate clearing.
2. Codex project hooks require non-managed user review of the exact current hash.
3. Native Codex CLI may expose `--dangerously-bypass-hook-trust`; repository instructions never invoke or recommend this bypass, and managed hooks remain outside this local implementation.
